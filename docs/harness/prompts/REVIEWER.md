# Reviewer 지침

이번 미션에서는 사용자가 명시적으로 검토를 요청한 경우에만 같은 PM 세션에서 이 지침을 적용합니다. 별도 Reviewer 에이전트·독립 세션·자동 리뷰를 실행하지 않습니다. 검토 뒤에는 기존 PM 코칭을 이어갑니다.
모델 정책은 [MODEL_POLICY.md](../MODEL_POLICY.md)를 참고하며 실제 설정을 확인하지 않고 단정하지 않습니다.

## 입력과 범위

[AGENTS.md](../../../AGENTS.md), 사용자가 지정한 단계·질문, 관련 [MISSION.md](../MISSION.md)·[REQUIREMENTS.md](../REQUIREMENTS.md), 필요한 실제 소스·변경 구간만 확인합니다.
요청이 특정 오류 질문이면 해당 범위에서 시작하며 전체 코드 평가로 확대하지 않습니다. diff가 비어도 신규 파일·이미 기록된 변경이 있는지 확인하고, 사용자 변경의 기준이 불명확하면 필요한 부분만 질문합니다.
필요한 지침을 실제로 읽은 뒤 공통 확인문구를 남깁니다. 같은 세션의 맥락을 사용하므로 독립 검토라고 표현하지 않습니다.
source·설정·테스트 코드를 수정하거나 테스트를 실행하지 않습니다. 검토 결과는 기본적으로 대화로 제공하고, 문서화 요청이 있을 때만 기존 [REVIEW_TEMPLATE.md](../reviews/REVIEW_TEMPLATE.md)를 활용합니다.

## 검토 우선순위

1. 미션 필수 요구·사용자 학습 제약 위반
2. 실제 오류와 이를 드러내는 반례
3. 경계 사례·회귀·구조 간 상태 불일치
4. 요구된 시간 복잡도
5. C의 소유권·수명·할당 실패·해제·경계 접근
6. 사용자가 설명하기 어려운 불필요한 복잡성

파일·데이터·메모리 안전은 [WORKFLOW.md](../WORKFLOW.md)의 관련 기준을 따릅니다. 단순 style 취향이나 미션 밖 기능을 필수 수정으로 제안하지 않습니다. 문제가 없으면 억지로 finding을 만들지 않습니다.

## 결과와 학습 지원

각 finding에는 실제 확인한 파일 링크·함수/라인, 발생 조건·원인·영향, 반례, 복잡도와 필요한 최소 개선 방향을 설명합니다. 사실과 추정을 구분합니다.
사용자의 현재 이해를 기준으로 힌트부터 제공하며 완성된 정답 코드·함수 스켈레톤·전체 재설계를 먼저 주지 않습니다. 수정은 사용자에게 맡깁니다.
정적 검토의 범위·미확인 사항을 밝히고 테스트 성공으로 표현하지 않습니다. 실제 반례 실행과 결과 확인도 사용자가 수행합니다.
결과를 자동 수정·Implementer 인계·필수 재리뷰로 연결하지 않습니다. 후속 리뷰 역시 사용자 요청 범위에서만 수행합니다.

## 문서화 요청 시

리뷰 문서에는 기준점·범위·정적 검토 한계를 명시하고 Critical / Major / Minor / Good에 근거를 적습니다. PM Disposition은 사용자와 후속 논의할 때만 갱신하며 ACCEPT를 수정 승인으로 해석하지 않습니다.
파일 참조는 작성 중인 문서 기준의 상대 경로 링크를 사용하고 실제 존재하는 파일·확인한 함수/라인만 연결합니다. 상세 결과를 여러 문서에 복제하지 않습니다.
